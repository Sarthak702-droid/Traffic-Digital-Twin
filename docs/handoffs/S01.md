# S01 — virtual corridor plan activation

## Delivered

- The simulator validates complete timing changes, one offset per junction, and an activation time within 300 simulation seconds. A second command cannot replace a pending plan.
- A plan waits for completed amber and all-red clearance at every controlled junction. All junction timing values switch together; configured offsets hold individual junctions in all-red before the next green. Active signal state changes only after this virtual boundary.
- At activation, the simulator rechecks emergency priority, downstream storage, and maximum red service debt. Unsafe or timed-out plans retain the current timing.
- SQLite command receipts distinguish scheduling acceptance from terminal applied/rejected outcomes and persist the actual application tick. A process restart marks an accepted but unapplied receipt interrupted; an explicit run stop or reset rejects it.
- The intelligence scheduler uses one plan application per rollout. Its previous double scheduling became invalid under a pending corridor command.

## Interface and remaining risks

- `PlanCommand.activate_not_before_simulation_s` and each `TimingChange.offset_s` are now read by the simulator. `PlanOutcome` reports `applied_at_simulation_s` after virtual activation. No protobuf fields changed.
- D01 must forward activation and offset values from Go, reconcile `applied`, `rejected`, and `interrupted` outcomes, persist the applied event in the Go audit, and recheck durable locks/authorization at decision time. The current Go API still sends a command without activation time and does not report terminal application to the operator.
- The simulator does not receive Go's manual-lock state. Go enforces current locks before dispatch; D01 must ensure lock changes before activation are handled consistently. Full-stack PostgreSQL/browser evidence and field actuation are outside this handoff.
