# S03 — bounded recommendations and explicit outcomes

## Delivered

- `comparison-scoring-v1.1` declares a 120-second matched window, at most five candidates including current timing, at most three returned alternatives, one concurrent analysis per intelligence process, a 1.5-second internal deadline, and a 10 weighted-point minimum gain. The weights and minimum are engineering assumptions pending E01/E02 evaluation.
- `Model.analyze` returns `recommend` only for a safe candidate beating the current plan by more than the declared minimum. It returns `no_action` with no actionable recommendation when current timing wins or gain is too small. Missing/stale history, incomplete snapshots, unsafe current timing, timeouts, and a full analysis slot return `cannot_evaluate` with no actionable recommendation.
- Actionable recommendation fields and IDs bind the run, source session, snapshot sequence, config, model/metric/scoring versions, and forecast origin. A changed input epoch generates a different ID even at the same simulation time and timing plan.
- Deadline and concurrency failures return four `compute_unavailable` horizon entries. `Predict` reports `FAILED_PRECONDITION` if analysis has no numeric forecast, avoiding an index error.
- Existing scenario-specific scoring remains separate for normal, emergency priority, and emergency recovery. The bound is process-local; a future multi-process deployment needs an external aggregate limit or one configured process.

## Verification

- Focused RED→GREEN checks covered no-demand and below-threshold outcomes, zero deadline, concurrent analysis, incomplete and unsafe snapshots, candidate cap, emergency recovery, and the `Predict` RPC failure path.
- Full Python, contract, Go, and web results are recorded at integration. The tests here establish model and service behavior, not full-stack operation or benchmarked resource capacity.

## Downstream handoff

- D01 must reject old recommendations when a later `no_action`, `cannot_evaluate`, or source epoch arrives. The current Go analysis loop can retain a prior pending recommendation for 30 seconds, so this Python outcome alone does not make stale approval safe.
- E01/E02 must freeze and evaluate the scoring weights, minimum gain, deadline, fairness and no-benefit cases on the benchmark protocol. P01 must measure the configured budgets on the target machine; the 1.5-second deadline is a protective limit, not a measured capacity claim.
